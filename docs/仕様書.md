# 配分ルート最適化プログラム 仕様書

## 1. 概要

複数の配送先へ、複数の補給地点を拠点とする車両群で物資を配り切るときの最適な巡回ルートを求めるプログラム。「最も時間のかかる車両の所要時間（メイクスパン）」を最小化し、全車両がなるべく同時に・早く作業を終えられる配車を計算する。

補給地点は固定ではなく**候補リストから選定する**。処理は 2 段構え。

1. **補給地点の選定**（`depot_selection.py`）— 候補セットから最良 K 地点（既定 5）を選び、各地点への車両台数を配分する。
2. **配分ルート最適化**（`distribute_solver.py`）— 選定結果を前提に各車両の順路を確定する。

移動時間は Mapbox Matrix API による道路ネットワーク上の実測運転時間を用い、Google OR-Tools の経路最適化ソルバーで解く。

- **言語 / 実行環境**: Python 3.12 以上、パッケージ管理は `uv`
- **主要依存**: `ortools`（経路最適化）、`python-docx`（レポート生成）、`numpy`
- **外部API**: Mapbox Directions Matrix API（利用不可時は OSRM へ自動フォールバック）

---

## 2. 前提モデル

- 車1台に積み込める機材の数は **`VEHICLE_CAPACITY`（容量C、既定1）**。「補給地点で最大C個積む → 最大C地点へ順に配る → 補給地点へ戻る」を繰り返すシャトル動作を行う。
- 各補給地点には選定で決まった数の機材（`stock`）が置かれ、それを1回で積み切れる台数 `ceil(stock / C)` の車両が待機する。C=1 なら「1局1台」（車両数＝地点数）。
- 車両と補給地点に**固定の所属はない**。在庫が尽きない限り、どの車両もどの補給地点からでも積んでよい（「あるデポを多用する」のは最適化の結果であって前提ではない）。
- 各補給地点は在庫（`stock`）個ぶんだけ供給できる。
- 全車両は共通の**仮想スタート（garage）**から発進・帰着する。garage との移動時間は 0（車両の初期位置を前提に置かない割り切り）。

**目的関数**: 全車両のルート所要時間の最大値（メイクスパン）を最小化。

## 4. 入力データ（`waypoints.py`）

### 配送先（waypoints）
- 全33地点。各要素は `id / name / lat / lon / group`。
- `group`: 1 = 点1〜23、2 = 点24〜33（KMLのアイコンスタイル区分に対応）。
- **ソルバーの配送先には `group == 1` の23地点のみを使用**（`main.build_inputs()`）。

### 補給地点の候補（candidate_supply_points）
- 12セット。各要素は `code / name / lat / lon / address / station / rental`。
- 各セットは以下の条件をすべて満たす「拠点 × 駅 × レンタカー営業所」の組（詳細は `補給地点候補セット.md`）。
  1. 機材を配置できる拠点であること
  2. 人員を集めるための駅が近隣にあること
  3. 車両を調達するレンタカー営業所が駅の徒歩圏にあること
- 座標は各セットのレンタカー営業所住所を国土地理院ジオコーダで変換した実測値。
- **`stock` は持たない**。配置台数は選定の結果として決まる。
- `NUM_DEPOTS_TO_SELECT = 5`（採用する地点数）。

> 採用地点の配置台数の合計（23）＝ 配送先数（23）となる。

---

## 4b. 補給地点の選定（`depot_selection.py`）

「1局1台」では車両1台の所要時間が `積込 + 移動(拠点→担当地点) + 作業` で確定するため、問題は**どの K 地点を選び、どの地点をどの拠点に割り当てるか**に帰着する。これは施設配置問題の **p-center 問題**にあたる。

| 状況 | 解法 |
|---|---|
| 台数上限なし | 各地点を「選択拠点のうち最短の拠点」へ割り当てる（最寄り割当が最適） |
| 台数上限あり | ボトルネック割当（閾値の二分探索 + 増加路法による二部マッチング） |
| 候補 ≦ 20 件 | 全組合せを総当たり（**厳密解**。12C5 = 792 通り） |
| 候補 > 20 件 | 1地点ずつ追加する貪欲法（近似） |

評価値はメイクスパン、同点なら総所要時間で比較する。

## 5. 処理フロー

```
fetch_data.py（事前・任意）
    └─ Mapbox Matrix API → cache/mapbox_matrix.json

main.py
    1. build_inputs()          … targets(group==1) と depots を組み立て
    2. build_travel_time()     … キャッシュ or API から移動時間 callable を生成
    3. solve_distribution()    … OR-Tools で最適化
    4. print_result()          … コンソールへ結果表示
```

### 5.1 移動時間の取得（`mapbox.py`）

- 全地点対の運転時間を Mapbox Matrix API から取得し、`(lat,lon),(lat,lon) → 分` の callable を返す。
- Matrix API は1リクエスト最大25座標のため、`BLOCK_SIZE = 12` のブロック対に分割して取得。
- **キャッシュ**: 座標列 + プロファイルの SHA-256 ハッシュをキーにする。地点や profile を変えるとキーが変わり古いキャッシュは自動失効。`--max-age` で TTL 失効も可能。
- 到達不能（None）は `1e9` 分で埋める。
- トークンは環境変数 → `.env` の順に読む。

### 5.2 最適化ソルバー（`distribute_solver.py`）

`solve_distribution()` が司令塔となり、以下を順に実行する。

1. **check_stock**: 在庫合計 ≧ 配送先数 を検証（不足なら `ValueError`）。
2. **build_node_model**: ノード列を構築。
   - `[0 .. nT-1]`: 配送先（demand −1、必須訪問）
   - `[nT .. nT+stock合計-1]`: pickupユニット（在庫1個=1ノード、demand +1、任意訪問）
   - 末尾1個: garage（demand 0、全車両の start/end）
3. **RoutingModel構築**: 全車両を garage から発進・帰着。
4. **add_time_dimension**: アークコスト=所要時間（移動＋作業/積込）。garage 出入りは0。`SetGlobalSpanCostCoefficient(MAKESPAN_WEIGHT=10000)` でメイクスパンを強く最小化。時間は `TIME_SCALE=100`（0.01分単位）で整数化。
5. **add_capacity_dimension**: 容量C（`AddDimensionWithVehicleCapacity`）。積込で+1、配送で−1 を累積し、積載量が 0〜C に収まるよう制約する（積まずに配る・C個を超えて積む、を禁止）。
   - **add_delivery_limit**: `max_deliveries_per_vehicle` を指定したときのみ、1台の配送件数（積み直し込み）に上限をかける。
   - **build_initial_routes**: 各車両が待機デポで最大C個積み、近い地点から配る自明解を作り、探索の種にする。
6. **add_pickup_options**: pickupユニットを `AddDisjunction(penalty=0)` で任意訪問（未使用在庫はスキップ可）。
7. **build_search_params**: 初期解 `PATH_CHEAPEST_ARC`、改善 `GUIDED_LOCAL_SEARCH`、時間制限つき。
8. **extract_solution**: ノード連鎖を人間可読な順路へ復元。「使用したデポ」は結果として算出。

## 6. パラメータ

`main.py` 冒頭の定数で設定する（`--capacity` などコマンドライン引数で上書き可）。

| 定数 / 引数 | 既定 | 意味 |
|------|----------------|------|
| `VEHICLE_CAPACITY` / `--capacity` | 1 | 1台に積み込める機材の数（＝1回の積込で配れる地点数） |
| `MAX_DELIVERIES_PER_VEHICLE` / `--max-deliveries` | None（＝積載量と同じ） | 1台あたりの配送件数上限。積載量より大きくすると積み直し往復を許す |
| `SERVICE_MIN` | 10 | 配送先1件あたりの作業時間（分） |
| `RELOAD_MIN` | 5 | 補給地点での積込時間（機材1個あたり、分） |
| `NUM_DEPOTS_TO_SELECT`（waypoints.py） | 7 | 採用する補給地点の数 |
| `--time-limit` | 60 | ルート最適化の探索時間上限（秒） |

> 補給地点の選定（p-center）は「各地点へ拠点から直行する」前提で評価するため、C>1 では選定時点のメイクスパンは参考値。実際の所要時間はルート最適化の結果を見る。

## 7. 出力

### 7.1 コンソール（`main.py`）
```
メイクスパン: <分>

[車両k] 配送=N件 使用デポ=... 所要=T分
   補(補給X) -> 配[地点名] -> 補(...) -> ...
```

戻り値 `result` の構造:
```python
{
  "makespan_min": float,          # メイクスパン（分）
  "routes": [
    {
      "vehicle": int,             # 車両番号
      "deliveries": int,          # 配送件数
      "depots_used": [str, ...],  # 結果的に使ったデポ名
      "time_min": float,          # このルートの所要時間（分）
      "steps": [str, ...],        # "配[名]" / "補(名)" の連鎖
    }, ...
  ]
}
```
解なしの場合は `None`。

### 7.2 レポート（`make_report.py`）
`docs/配分ルート最適化_レポート.docx` を生成。目的・前提モデル・ロジック・入力データ・実行結果（車両別の順路テーブル＋1行順路）を含む。既定フォントは Yu Gothic。

## 8. 実行方法

```bash
# 依存インストール
uv sync

# （任意）Mapbox 移動時間を事前取得・キャッシュ更新
uv run fetch_data.py                 # 有効キャッシュがあれば再取得しない
uv run fetch_data.py --force         # 強制再取得
uv run fetch_data.py --max-age 3600  # 3600秒より古ければ再取得
uv run fetch_data.py --profile driving-traffic  # プロファイル指定

# 最適化を実行
uv run main.py                                 # 積載量 1(1局1台)
uv run main.py --capacity 3                    # 1台に機材3個まで
uv run main.py --capacity 2 --max-deliveries 4 # 2個ずつ、積み直して最大4地点

# 発表用レポート(docx)を生成
uv run make_report.py
```

### 事前準備
`.env` に Mapbox アクセストークンを設定する:
```
NEXT_PUBLIC_MAPBOX_ACCESS_TOKEN=pk.xxxxxxxx
```

## 9. 補足・設計上の割り切り

- garage の座標は `(0.0, 0.0)` で未使用。garage との移動時間を0にすることで、車両の初期位置を前提にしない。
- 在庫上限は「pickupノードを stock 個しか作らない」ことで構造的に保証。
- 同一座標（複数在庫の pickup など）は行列上1点に集約。未知座標が来た場合は callable が大きな値（`1e9`）を返す。
- メイクスパン重視のため、総距離より最遅ルートの短縮を優先する重み設計になっている。
