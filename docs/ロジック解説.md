# 人員配置ルート最適化 ― ロジック解説（初心者向け）

このプロジェクトは「**たくさんの地点へ、機材と測定人のセットを最速で配り終えるには、車をどう走らせればいいか**」を計算するプログラムです。
このドキュメントは、プログラミング初心者でも全体像がわかるように、やさしく説明します。

---

## 1. そもそも何をしたいの？

地図上に **配り先（経由地）** がたくさんあります。
そこへ「機材＋測定する人」のセットを **1地点につき1個ずつ** 届けたい。

セットは **補給地点（デポ）** に置いてあります。
車はそこでセットを積んで、配り先まで運びます。

ゴールはシンプルで、

> **全部配り終わるまでの時間を、できるだけ短くする**

ことです。一番遅い車が終わった時刻が「全体の完了時刻」になるので、それを縮めます。
この「全部終わるまでの時間」を専門用語で **メイクスパン** と呼びます。

---

## 2. 大事なルール（制約）

現実に合わせて、いくつかルールがあります。

1. **車1台に積めるセットの数（積載量）は決まっている**
   → 「補給地点で積めるだけ積む → 順に配る →（必要なら）補給地点に戻って積み直す」をくり返します。
   積載量は設定で変えられます（既定は1。1なら「1回1セット」）。

2. **補給地点は候補リストから選ぶ**
   → あらかじめ用意した候補（駅とレンタカー屋がセットになった拠点など）の中から、
   **一番よいK か所だけ**を採用します（埼玉のシナリオでは7か所）。どこを選ぶかもプログラムが決めます。

3. **各補給地点に置くセットの数（在庫）も、選定と同時に決まる**
   → 各配り先を一番近い採用拠点の担当にし、担当の数だけセットを置きます。

4. **車の台数は「在庫 ÷ 積載量（切り上げ）」**
   → 各拠点のセットを1回で積み切れる台数の車が、その拠点で待機します。
   積載量1なら配り先の数と同じ台数、積載量3なら約3分の1の台数になります。

## 3. ファイルの構成

```
route_calcurate/
├── depot_planner/
│   ├── cli.py          ← コマンドで動かす入口（uv run depot-planner ...）
│   ├── server.py       ← 画面（GUI）の裏側
│   ├── static/         ← 画面そのもの（地図・入力欄・結果表示）
│   ├── runner.py       ← 計算の段取り役（①選定 → ②ルート）。画面からもコマンドからもここを呼ぶ
│   ├── solver.py       ← ①どの補給地点を使うか決める
│   ├── routing.py      ← ②車ごとのルートを計算する本体（頭脳）
│   ├── travel_times.py ← 移動時間を取ってきて保存しておく
│   ├── scenario.py     ← シナリオ（地点や条件のセット）の読み書き
│   └── report.py       ← 報告書（Word）・CSV を作る
├── scenarios/          ← シナリオのファイル（地点データと条件）
└── docs/               ← このドキュメントなど
```

それぞれの役割：

| ファイル | 役割 | たとえると |
|----------|------|-----------|
| `scenarios/*.json` | 地点の緯度経度・補給地点候補・条件のデータ | 材料 |
| `solver.py` | どこに拠点を置き、何セット置くか決める | 仕込み |
| `routing.py` | 最適なルートを計算する | 料理人 |
| `runner.py` | データを渡して計算させ、結果をまとめる | 注文係 |
| `cli.py` / `server.py` | コマンド・画面から注文を受け付ける | お店の窓口 |

## 4. データの形（`scenarios/*.json`）

### 配り先（目的地）

1地点はこんな形のデータです。

```json
{"id": "T01", "name": "点1", "lat": 36.2203, "lon": 139.4971, "enabled": true}
```

- `lat` / `lon`：緯度・経度（地図上の位置）
- `enabled`：false にすると、消さずに計算から外せます

### 補給地点の候補

```json
{"id": "P1", "name": "東洋大学(川越)", "lat": 35.9375, "lon": 139.4537,
 "group": "実績", "status": "candidate", "note": "駅: 東武 鶴ヶ島駅 / レンタカー: ..."}
```

- `status`：`candidate`（選定の対象）/ `required`（必ず使う）/ `excluded`（使わない）
- `note`：人員を集める駅や、車を借りるレンタカー屋などのメモ
- **在庫（置くセットの数）は書きません**。選定の結果として決まるからです。

## 5. 計算の流れ（`runner.py`）

画面の「シミュレーション実行」か、コマンド `uv run depot-planner run <シナリオ>` で、次の順に進みます。

```
① データを用意する        （シナリオを読み込む）
② 移動時間を取ってくる    （道路を走ったときの実際の時間。一度取った分は保存して使い回す）
③ 補給地点を選ぶ          （solver.py → K か所と、各拠点に置くセットの数が決まる）
④ ルートを計算する        （routing.py → 積載量を守りながら、車ごとの順路が決まる）
⑤ 結果を表示・保存する    （画面の地図と表、または runs/ フォルダに Word・CSV）
```

③の選び方は「**全部の組み合わせを試す**」です。候補21か所から7か所を選ぶ組み合わせは
11万通りほどなので、コンピュータなら一瞬で全部試せます。
だから「たぶんこれが良さそう」ではなく、**確実に最適**な選び方が出ます
（ただし③は「各配り先へ拠点から直行する」として評価しています）。

④のルート計算 `solve_routes()` の中は、次の部品でできています。

| 順番 | 部品 | やっていること（やさしく言うと） |
|------|------|--------------------------------|
| 1 | `build_node_model` | 地図上の場所を、計算しやすい「番号付きの点」に並べ替える |
| 2 | Time（時間） | 移動時間＋作業時間を数え、「一番遅い車を速くする」目標を設定 |
| 3 | Load（積載量） | 「積めるのは C 個まで」のルールを設定 |
| 4 | Deliveries（配送件数） | 「1台が配るのは最大◯か所まで」のルールを設定 |
| 5 | Disjunction | 「どの補給地点から積むかは自由」を設定 |
| 6 | 初期解 | 「待機場所で積めるだけ積んで、近い順に配る」たたき台を作って渡す |
| 7 | 探索 | 答えの探し方を設定して、時間いっぱい改善させる |

## 6. ここが肝心 ― どうやって「最適なルート」を見つけるの？

実は、このプログラムは **「ルートを自分で組み立てて」いません**。
代わりに、**「ルールと目標」だけを伝えて、専用の計算エンジン（Google OR-Tools）に解かせています。**

イメージはこうです。

> 「この点とこの点をつなげていい。ただし “積載量” と “在庫の上限” は守って。
>  その中で、一番時間がかかる車を一番短くして！」

とお願いするだけ。あとはエンジンが、つなぎ方の組み合わせを高速に試して、良い答えを見つけてくれます。

### どうやって試すの？（探し方）

1. **まずたたき台を1つ作る**（各車が待機場所で積めるだけ積み、近い点から配る）
2. **少しずつ入れ替えて改善する**
   - 「この配り先を別の車に渡したら、全体が速くなる？」
   - 「順番を入れ替えたら短くなる？」
   を何千回も試す
3. **時間切れ（既定は30秒。設定で変えられる）になったら、その時点で一番良かった答えを返す**

なので、答えは「数学的に絶対の最適」ではなく「**決めた時間で見つけた、とても良い答え**」です。

## 7. 「積載量」をどう守らせているか（仕組みのコツ）

ちょっとした工夫があります。

- **積載量** という数字を用意し、「補給地点で +1、配り先で −1」と変化させます。
- そして「積載量は **0 から C まで**」というルールを置きます（C は1台に積める数）。

すると…

- 積んでいない（0）のに配り先へ行く → −1になってルール違反 → **禁止**
- C 個を超えて積む → C+1 になってルール違反 → **禁止**

結果として、**必ず「積む → 配る」の順番で、積める数を守って**しか動けなくなります。
C=1 なら「補給 → 配る → 補給 → 配る…」、C=3 なら「3個積む → 3か所配る」のような動きになります。
わざわざ複雑な命令を書かなくても、数字のルール1つで現実の動きを再現できる、というわけです。

### 在庫の上限も同じ発想

補給地点ごとに「積む場所（積込ノード）」を **在庫の数だけ用意**しておきます。
6個しか置かなければ、7回目は積む場所が無い → **自動的に在庫オーバーを防げます**。

## 8. 結果の読み方

コマンドで実行すると、ルートの部分はこんな出力が出ます（積載量3の例）。

```
=== 2. 配分ルート最適化 ===
最長所要 102.5 分 / 車両 14 台(積載量 3・1 台最大 3 件)  探索 20.0 秒
[車両 2] 配送 3 件  所要 97.8 分
     待機(レンタルスペース(栗橋)) → 補(レンタルスペース(栗橋))×3 → 配[点13] → 配[点5] → 配[点8]
```

- **最長所要**：全車が配り終わるまでの時間（これを最小化している）
- `[車両 2]`：2番の車の話
- `配送 3 件`：この車が配った地点の数
- `所要 97.8 分`：この車が配り終えるまでの時間（補給地点に戻る時間は含まない）
- 下の行：実際の順路。`補(栗橋)×3` ＝ 栗橋で3個積む、`配[点13]` ＝ 点13へ配る

画面（GUI）では、結果タブの「車両ごとの順路」の行を押すと、地図上でその車のルートが強調されます。

「どの補給地点から積んだか」は **最初から決めていたのではなく、計算の結果そうなった** だけ、という点がポイントです。

## 9. 動かし方

ターミナルで、プロジェクトのフォルダに移動して：

```bash
uv run depot-planner gui                         # 画面で操作する
uv run depot-planner run saitama_all33           # コマンドで実行する
uv run depot-planner run saitama_all33 --capacity 3   # 1台に3個積める場合
```

`uv` が必要な部品（ortools など）を自動でそろえて実行します。

### 設定を変えたいとき

画面なら「条件」タブで変えて「保存」します。ファイルで直すなら、シナリオの `params` を書き換えます。

```json
"params": {
  "num_depots": 7,          ← 採用する補給地点の数
  "service_min": 10,        ← 1地点での作業時間（分）
  "reload_min": 5,          ← 1個積み込む時間（分）
  "routing": {
    "vehicle_capacity": 1,  ← 1台に積めるセットの数
    "max_deliveries": null, ← 1台が配る上限（null なら積載量と同じ＝積み直しなし）
    "time_limit_sec": 30    ← ルート計算にかける秒数
  }
}
```

例えば `vehicle_capacity` を増やすと車の台数は減りますが、1台が何か所も回るので、最長所要は長くなります。

## 10. いまの「割り切り」（今後よくできる点）

このプログラムは、わかりやすさ優先でいくつか簡略化しています。

1. **補給地点の選定は「直行」で評価**
   → 積載量が2以上のとき、選定の段階では「1台が何か所も回る」ことを考えていません。
   選んだ拠点のもとで、ルート計算が実際の所要時間を出します。
2. **帰り道は数えない**（配り終わった時点で終了。補給地点へ戻る時間は含まない）
3. **地図のルート線は表示用**（Mapbox Directions API で立ち寄り順に道路沿いの線を引いている。線は計算とは別に取っているので、所要時間の計算に使った経路と細部が違うことがある。取得できないときは直線）
4. **答えは「とても良い近似」**（ルート計算は決めた時間内の探索なので、厳密な最適とは限らない）

---

### まとめ

- やりたいこと：**補給地点を選び、全地点へ最速でセットを配る車のルートを決める**
- やり方：**ルールと目標をエンジンに伝えて解かせる**（自分でルートは組まない）
- コツ：**「積載量0〜C」という数字のルールだけで、現実の動きを再現している**
